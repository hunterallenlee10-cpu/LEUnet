# H1 Performance — Moved to Its Own Repo

**As of 2026-09-01, H1 Performance is its own website, built from its own
repo: <https://github.com/hunterallenlee10-cpu/h1-performance>.**

The build spec that used to be this file — every settled decision about the
program page, the sourcing rules for its figures, the testimonial rules and
their dated amendments — moved with the page and is `docs/H1.md` there. Read
that before touching anything H1-related; nothing in it was loosened by the
move.

This file records what the split left behind here, and why.

## 1. What left

Everything that was the page:

| Left this repo | Now |
| --- | --- |
| `app/h1-performance/page.tsx` | `app/page.tsx` in the H1 repo — the page is that site's homepage |
| `app/api/h1-consultation/route.ts` | Same path in the H1 repo. Leads still deliver to the LEU inbox by default |
| `components/h1/` — 12 components | Same path |
| `data/h1.ts`, and the H1 interfaces in `types/index.ts` | Same paths |
| `public/h1/` — coach and athlete photos | Same path |
| The two H1 blocks in `app/globals.css` (hero readout, `.h1-live` / `.h1-tap`) | Same file there. Nothing else here used them; `BmAudienceSection` notes why it never did |
| `H1_TO_EMAIL` in `.env.example` | The H1 project's environment |

## 2. What stayed, and why

H1 is still one of the three Lee Enterprises Unlimited ventures, and everything
that says so on this site stays:

- **The venture itself.** `data/ventures.ts` (the homepage card and the footer
  list), `VENTURE_COLORS.h1` in `lib/colors.ts`, the H1 option on the contact
  form in `data/contact.ts`, and the H1 entries in `data/services.ts`.
- **The logo.** `public/logos/h1-performance-white.png`: the homepage card
  renders it. The H1 repo carries its own copy.
- **Invoicing.** `POST /api/stripe/invoice` still accepts `ventureId: "h1"`.
  The H1 site takes no payment; H1 clients are invoiced from here through the
  shared Stripe account, tagged `h1` for reporting — `docs/STRIPE.md` §2.
- **Thread's H1 apparel line** in `data/thread.ts`. Those are Thread products,
  and the H1 site's footer links to them.
- **The metadata copy** in `app/layout.tsx` naming H1 as one of three ventures.

## 3. The wiring, and the one variable that drives it

Every path from this site to the H1 site resolves to one value: the
`NEXT_PUBLIC_H1_SITE_URL` environment variable, with a fallback to Vercel's
default alias for a project named `h1-performance`. The fallback and the
normalisation live in `config/h1-site.mjs`; `next.config.mjs` resolves the
variable through it for the redirect and hands the result to the app through
its `env` key; app code imports `H1_SITE_URL` from `lib/h1-site.ts`.

| Where | What it does |
| --- | --- |
| `next.config.mjs` | Permanent redirect of `/h1-performance`, and anything under it, to the H1 site, so old links and search results carry over |
| `data/navigation.ts` | `venturePages.h1` is the H1 site. The Ventures menu and the footer read it |
| `components/layout/MainHeader.tsx` | `handleNavClick` treats an absolute URL like a route: a full navigation, not a scroll |
| `data/websites.ts` | The H1 entry in `websitePortfolio` links out. `WebsitesWorkSection` and `docs/WEBSITES.md` §3.5 now describe the portfolio as three routes here plus H1 on its own domain |

**To do once the H1 site has its domain:** set `NEXT_PUBLIC_H1_SITE_URL` to it
in this project's Vercel environment, no trailing slash, and redeploy. Until
then every link goes to the fallback, which is only right if the H1 Vercel
project really is named `h1-performance` and that alias was free — so set the
variable rather than relying on it.

`config/h1-site.mjs` is a plain JavaScript module on purpose: `next.config.mjs`
cannot import TypeScript, and the alternative was the same URL written twice.
It does not read `process.env` itself. Next inlines `NEXT_PUBLIC_*` reads at
build time only in the app's own TypeScript, not in a `.mjs` module — an env
read there reached the browser as a live lookup that always came back
undefined, which would have sent the header and footer to the fallback while
the redirect went to the configured domain. That is why the read sits in
`lib/h1-site.ts` and `next.config.mjs`, and the shared module only normalises.
