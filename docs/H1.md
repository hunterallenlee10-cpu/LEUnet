(<https://github.com/hunterallenlee10-cpu/h1-performance>), and on 2026-09-03
it came off this site altogether. Lee Enterprises Unlimited lists one venture
here now, Lee Marketing Mastery: Thread T-Shirts, the other venture when this

program page, the sourcing rules for its figures, the testimonial rules and

that before touching anything H1-related; nothing in it was loosened by either

## 3. What stayed, and why

- **The `/h1-performance` and `/h1/*` redirects** in `next.config.mjs`. They are
  the one thing here that still points at the H1 site, and they are deliberate:
  `/h1-performance` answered on this domain for months, so its inbound links,
  bookmarks and search placement are worth forwarding rather than throwing at a
  404. No page on this site links to them. Remove them only when the H1 site's
  own domain has held that traffic long enough that the old URL stops being
  followed — and expect a 404 for anyone still on an old link when you do.
- **`config/h1-site.mjs` and `NEXT_PUBLIC_H1_SITE_URL`**, because the redirects
  need a target. §5 has the wiring; it is smaller than it was.
- **Invoicing.** `POST /api/stripe/invoice` still accepts `ventureId: "h1"`.
  The H1 site takes no payment; H1 clients are invoiced from here through the
  shared Stripe account, tagged `h1` for reporting — `docs/STRIPE.md` §2. This
  is a back-office route behind `STRIPE_ADMIN_TOKEN`, not a page, so it says
  nothing to a visitor about who LEU's ventures are.
- **Thread's H1 apparel line** in `data/thread.ts` — six shirts carrying the H1
  Performance mark. Those are Thread products, they are Thread's to sell, and
  the H1 site's footer links to them. Pulling them is a merchandising decision
  about Thread's catalog, not part of removing a venture listing, and it would
  take out over half of Thread's non-placeholder tees. It was left alone here on
  purpose; decide it as its own change.

## 5. The wiring that is left

`NEXT_PUBLIC_H1_SITE_URL` drives the redirects and nothing else. The fallback
and the normalisation live in `config/h1-site.mjs`; `next.config.mjs` resolves
the variable through it. There is no longer an `env` key handing the value to
the app, because no app code reads it.

The redirect is a 308 (permanent) only once `NEXT_PUBLIC_H1_SITE_URL` is set;
while it is unset it targets the fallback — Vercel's default alias for a project
named `h1-performance` — and stays a 307, so no browser caches a redirect to the
wrong host. If that variable is not yet set in this project's Vercel
environment, set it to the H1 site's origin (no trailing slash, Production and
Preview) before the next deploy, and confirm the target answers first: a 308 is
cached indefinitely and treated by crawlers as a permanent move.

`config/h1-site.mjs` is a plain JavaScript module on purpose: `next.config.mjs`
cannot import TypeScript. It does not read `process.env` itself — Next inlines
`NEXT_PUBLIC_*` reads at build time only in the app's own TypeScript, not in a
`.mjs` module, where an env read reached the browser as a live lookup that
always came back undefined. That is why the caller passes the variable in.
